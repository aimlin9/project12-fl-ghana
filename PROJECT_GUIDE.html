1The Big Picture

Your project predicts which students are "at-risk" of dropping out or failing, across 3–5 Ghanaian schools, without any school sharing its raw student data. This is the core innovation.

The Problem: Student data is sensitive and protected by privacy laws. Schools cannot legally send student records to a central server. But a model trained on only one school's data won't generalise well to other schools.
The Solution — Federated Learning: Each school trains a local AI model on its own data. Only the model update (not the data) is sent to the server. The server combines all updates into a better global model. No raw data ever leaves the school.

On top of Federated Learning, the project adds two extra layers of security:

  • Differential Privacy (DP-SGD) — adds mathematical noise during training so the model update cannot be reverse-engineered to reveal individual student records
  • Paillier Homomorphic Encryption — encrypts the model update before it is sent, so even the server never sees the raw update values
What changed since the first draft of this guide: the system now trains on the real OULAD dataset (32,593 records) instead of synthetic data, a round-1 aggregation bug was found and fixed, and Objective 1 (federated ≈ centralised accuracy) is now backed by an actual statistical significance test — not just eyeballed numbers. Details in Sections 3, 8, and 13.

3The Data Layer — Real OULAD School Databases

This section changed completely. The system originally used fully synthetic, hand-generated data. It now trains on the real Open University Learning Analytics Dataset (OULAD) — 32,593 real, anonymised student enrollment records, partitioned by real registration quarter.

Pipeline: download_oulad.py → oulad_features.py → partition_oulad.py

OULAD doesn't have literal "attendance" or "difficulty" fields — it's a university learning-analytics dataset, not a school register. The 8 model features are engineered as documented proxies:

FeatureDerived from real OULAD data
attendance_rateFraction of course days with any VLE (virtual learning environment) click activity
quiz_scoreAverage score on TMA/CMA assessments (excludes the final exam)
assignment_submission_rateAssessments submitted ÷ assessments scheduled
login_frequencyAverage VLE clicks per week
days_since_last_activityCourse length minus the student's last active day
course_difficulty1–5 ranking by that course-module's overall pass rate
prior_scoreScore on the student's earliest submitted assessment
engagement_indexTotal VLE clicks, scaled 0–100
at_riskTarget: 1 if real final_result was Withdrawn/Fail, else 0

OULAD has exactly 4 real registration quarters — 2013B, 2013J, 2014B, 2014J. This is the "non-IID" source in the project: each quarter's student population is genuinely different, not artificially generated to look different.

4The AI Model — client/model.py

The prediction model is a Multi-Layer Perceptron (MLP) — a feedforward neural network with three layers:

Input (8 features)
      ↓
Linear(8 → 64) + ReLU activation
      ↓
Linear(64 → 32) + ReLU activation
      ↓
Linear(32 → 1)  →  raw logit (no activation here)
      ↓
Sigmoid applied separately for evaluation → probability (0.0 – 1.0)
Important detail: the model outputs a raw logit, not a sigmoid probability. Training uses BCEWithLogitsLoss (numerically stable, applies sigmoid internally), and evaluation applies torch.sigmoid() separately to get a 0–1 probability.

Classification Threshold — Not a Fixed 0.5

The model does not use a fixed 0.5 cutoff to decide at-risk vs not. Every evaluation computes its own threshold via Youden's J statistic (the point on the ROC curve maximising TPR − FPR), recomputed per school, per round, from that round's actual data. In one real run this came out to 0.5821.

Training Details

  • Loss function: BCEWithLogitsLoss with a pos_weight that penalises missing at-risk students more heavily (handles class imbalance), capped at 10
  • Optimizer: Adam with learning rate 0.01
  • Local epochs: 3 per federated round
  • Batch size: 32 students per gradient step
  • Total parameters: 2,689 trainable weights

Evaluation Metrics

MetricWhat it measuresResult
F1-score (macro)Balance of precision and recall across both classesWithin 5pp of baseline — statistically confirmed (Section 13)
Balanced AccuracyAverage of sensitivity + specificity at the chosen threshold~93–95%
AUC-ROCModel's ability to rank at-risk students above safe ones, across ALL thresholds~0.97–0.98
Balanced Accuracy vs AUC — the exam trap: AUC is threshold-independent (the model's full ranking "ceiling"); balanced accuracy is measured at one specific chosen threshold (how much of that ceiling gets realised). AUC is always ≥ balanced accuracy for that reason — see the Defense Q&A guide (Section 14) for the full explanation.

5Privacy Protection — security/privacy.py

What is Differential Privacy?

Differential Privacy (DP) is a mathematical guarantee that says: "The output of this algorithm is nearly the same whether or not any single person's data is included."

In practice, it works by adding carefully calibrated random noise to the gradients during training. This is called DP-SGD (Differentially Private Stochastic Gradient Descent).

How it Works in the Code

Standard training:
  gradient = loss.backward()
  optimizer.step(gradient)

DP-SGD training:
  1. Compute per-sample gradients (one gradient per student)
  2. Clip each gradient to max_norm = 1.0
     (prevents any one student from dominating the update)
  3. Add Gaussian noise scaled by noise_multiplier = 1.1
  4. Average the noisy clipped gradients
  5. optimizer.step(noisy_gradient)

Privacy Budget — Epsilon (ε)

Epsilon (ε) is the privacy budget. It measures how much privacy is spent.

Lower ε = stronger privacy guarantee (but usually lower accuracy)
Higher ε = weaker privacy guarantee (but usually higher accuracy)

The project targets ε ≤ 3.0 per round with δ = 1×10⁻⁵
Extended sweep result: testing noise multipliers up to σ=20 (ε as low as 0.07) shows F1 stays remarkably strong — roughly 0.91 to 0.94 across the whole range. The privacy-accuracy trade-off is real (F1 is lowest at the strongest privacy setting) but the model tolerates it well.

Key Parameters

ParameterValueMeaning
noise_multiplier (σ)1.1 (default)Amount of noise added. Higher = more private
max_grad_norm1.0Maximum gradient size. Clips outliers
delta (δ)1×10⁻⁵Probability of privacy failure. Must be very small
Implementation library: Opacus 1.4 by Meta. It wraps the PyTorch model in a GradSampleModule that computes per-sample gradients efficiently. The client code tracks whether a model has already been wrapped (_dp_wrapped) to avoid double-wrapping across rounds 2+, which reuses the Poisson-sampled DataLoader via a reconstructed DPOptimizer.

6Encryption — security/crypto.py

What is Paillier Homomorphic Encryption?

Homomorphic encryption allows computations to be performed on encrypted data without decrypting it first. Paillier is a partial homomorphic encryption scheme that supports addition of encrypted values.

Normal encryption:
  Encrypt(5) + Encrypt(3) requires decryption first

Paillier encryption:
  Encrypt(5) ⊕ Encrypt(3) = Encrypt(8)   ← addition works on ciphertext!
  Decrypt(Encrypt(8)) = 8                 ← correct result

Why This Matters for Federated Learning

Without encryption: the server receives each school's model update in plaintext and could potentially analyse it to learn about students.

With Paillier encryption: the server receives encrypted updates, performs the weighted average while encrypted, and only decrypts the final combined result. Individual school updates are never visible to the server.

The Math — Weighted FedAvg in Encrypted Domain

school_alpha has 4,684 students, school_beta 8,845, school_gamma 7,804.
Total = 21,333 students.

Weight_alpha = 4684/21333 = 0.220
Weight_beta  = 8845/21333 = 0.415
Weight_gamma = 7804/21333 = 0.366

Server computes (all encrypted):
  result = Encrypt(update_alpha) × 0.220
         + Encrypt(update_beta)  × 0.415
         + Encrypt(update_gamma) × 0.366

One decryption gives the correct weighted average.

7The FL Client — client/client.py

This is the code that runs on each school's computer. It is a Flower NumPyClient — a standard interface that Flower uses to communicate with clients.

The fit() Method — Training Phase

def fit(self, parameters, config):
    # 1. If offline, raise so Flower records this round as a failure for this school
    if get_client_status(school) == "Offline":
        raise ConnectionError(f"Simulated network dropout for {school}")

    # 2. Load the global model weights from server
    set_flat_weights(self.model, parameters)
    old_weights = get_flat_weights(self.model)

    # 3. Train locally with DP-SGD (3 epochs)
    criterion = BCEWithLogitsLoss(pos_weight=self.pos_weight)
    for epoch in range(local_epochs):
        for X_batch, y_batch in train_loader:
            optimizer.zero_grad()
            logits = model(X_batch)              # raw logit
            loss = criterion(logits, y_batch)
            loss.backward()
            optimizer.step()   # DP noise added here by Opacus

    # 4. Compute the update (delta)
    new_weights = get_flat_weights(self.model)
    update = new_weights - old_weights

    # 5. Encrypt the update with Paillier
    encrypted_update = encrypt_weights(public_key, update)

    # 6. Send encrypted update + metrics back to server
    return parameters, num_samples, {
        "school_name": self.school_name,
        "encrypted_update": serialize(encrypted_update),
        "training_latency": elapsed_time,
        "epsilon": privacy_budget_spent,
    }

The evaluate() Method — Evaluation Phase

After each round of aggregation, the server sends the updated global model back. Each school evaluates it on its local test set (20% of its data), computes probabilities via sigmoid, picks the optimal threshold via Youden's J, and reports F1, balanced accuracy, and AUC-ROC back to the server.

8The FL Server Strategy — server/strategy.py

PaillierFedAvg Class

This is a custom implementation of the FedAvg algorithm that works with Paillier encrypted updates. It extends Flower's Strategy base class and overrides four methods, and now supports 3, 4, or 5 school nodes (not fixed to 3):

MethodWhen CalledWhat it Does
configure_fit()Start of each roundGenerates Paillier keys (Round 1 only), sends global model + public key to all schools
aggregate_fit()After all schools trainReceives encrypted updates, applies FedAvg weights homomorphically, decrypts result, updates global model
configure_evaluate()After aggregationSends updated global model to all schools for evaluation
aggregate_evaluate()After all schools evaluateAverages F1, accuracy, AUC scores; logs to database; updates dashboard telemetry
Bug found and fixed this iteration: round 1 could silently aggregate zero clients. configure_fit() was sampling clients the instant the Flower server's TCP port opened — before client threads had actually finished gRPC registration — so client_manager.num_available() sometimes read 0 at that exact moment, and round 1 would log all-zero metrics with an effectively untrained model. Fixed by having configure_fit() call client_manager.wait_for(num_clients, timeout=30) before sampling. Verified fixed at 3, 4, and 5 nodes, with and without DP/Paillier.

Logging and Audit Trail

After every round, two records are written:

  • logs/fl_metrics.db — SQLite table with round_id, node_id, F1, loss, accuracy, latency, comm_mb, epsilon for every school every round
  • logs/crypto_audit.jsonl — JSON audit log recording whether encryption was enabled, key size, number of clients, and whether all updates were encrypted

Telemetry Dictionary

A Python dictionary called telemetry_data is shared between the strategy and the FastAPI server. The strategy writes to it after every round; the API reads it and sends it to the React dashboard every 3 seconds.

How the Simulation is Started

1. Dashboard sends POST /api/start
2. FastAPI checks port 8088 is free
3. Starts run_fl_simulation() as a background task
4. run_fl_simulation():
   a. Creates PaillierFedAvg strategy
   b. Starts Flower gRPC server on port 8088 (separate thread)
   c. Waits for port 8088 to be ready
   d. Starts one client thread per online school
   e. Waits for Flower server to finish all rounds
   f. Marks simulation as complete
Why threads? The Flower server and all school clients run in the same Python process but in separate threads. This simulates a real distributed system on a single machine for demonstration purposes.

12How a Full Round Works — End-to-End Flow

SERVER: Generates Paillier key pair (once, Round 1 only)
↓
SERVER: Waits for all clients to finish gRPC registration (fixes the round-1 race)
↓
SERVER → ALL SCHOOLS: Sends global model weights + public key
↓
EACH SCHOOL: Receives global model, loads weights into local MLP
↓
EACH SCHOOL: Trains for 3 epochs with DP-SGD (Opacus adds noise to gradients)
↓
EACH SCHOOL: Computes update = new_weights − old_weights (2,689 numbers)
↓
EACH SCHOOL: Encrypts update with Paillier public key → 2,689 ciphertexts
↓
ALL SCHOOLS → SERVER: Send encrypted updates + metrics (F1, epsilon, latency)
↓
SERVER: Multiplies each encrypted update by its FedAvg weight (n_i / total)
↓
SERVER: Adds all weighted encrypted updates homomorphically (no decryption needed)
↓
SERVER: Decrypts once → gets weighted average model update
↓
SERVER: Adds update to global model: global = global + avg_update
↓
SERVER → ALL SCHOOLS: Sends updated global model for evaluation
↓
EACH SCHOOL: Evaluates on its 20% test set (Youden's J threshold) → reports F1, balanced accuracy, AUC-ROC
↓
SERVER: Logs metrics to fl_metrics.db + crypto_audit.jsonl
↓
DASHBOARD: Polls /api/telemetry → updates charts and cards
↓
Repeat for next round… then on the final round, the completion summary modal appears.

13Statistical Proof of Objective 1

The proposal's Objective 1 claims federated F1 lands within 5 percentage points of the centralised baseline. This is no longer just an eyeballed chart — it's a formal statistical test, run on real data.

Centralised Baseline F1
0.9386
Paired t-test p-value
0.9156
Cohen's d
−0.0505
Shapiro-Wilk
normal (p=0.48)

Method: the proposal's D4 methodology calls for testing across "5 independent random partitions" — but real OULAD only has 4 fixed registration quarters, so there's no way to draw 5 random school-level splits the way that language assumed for synthetic data. Instead, statistical_comparison.py holds the school/quarter assignment fixed and draws 5 independent bootstrap resamples of the train/test split, training both a centralised and federated (3-node, 50-round, no DP/Paillier) model on each seed.

Result: a paired t-test across the 5 (centralised, federated) F1 pairs gives p=0.9156 — far above the 0.05 significance threshold, meaning there is no statistically detectable difference between federated and centralised accuracy. Cohen's d of −0.05 confirms a negligible effect size.

DP and Paillier were deliberately switched off for this specific test, because it's isolating Objective 1 (accuracy parity) from Objective 2 (the privacy cost, tested separately by the privacy-accuracy sweep).
